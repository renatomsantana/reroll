COMO PUBLICAR UMA VERSÃO NOVA DO REROLL
=======================================

Como o app atualiza (a partir do 0.1.2-alpha)

O app pergunta ao GitHub, uma vez por abertura, se existe versão mais nova. Só pergunta — não baixa
nada. Se existir, a linha "Versão" nas Preferências passa a dizer "Existe uma atualização nova:
versão X" com um botão Atualizar. Quem clica responde duas perguntas ("deseja atualizar?" e "tem
certeza?"); aí sim ele baixa e reinicia sozinho pra aplicar.

Sem internet nada disso atrapalha: a pergunta falha em silêncio e o app funciona igual, offline.
Ninguém desinstala nada e ninguém perde presets, anotações ou preferências (esses ficam em
%APPDATA%\Reroll, que o instalador não toca).

O 0.1.1-alpha, que já está publicado, é a única versão com o comportamento antigo (baixava sozinho
e aplicava ao fechar). Quem estiver nela recebe o 0.1.2 desse jeito, e do 0.1.2 em diante vale a
regra de cima.

Onde: https://github.com/renatomsantana/reroll  (precisa ser PÚBLICO)

Primeira vez (só uma vez, pelo site — não precisa de git instalado)
-------------------------------------------------------------------

1. github.com -> New repository
       nome: reroll
       Public
       marcar "Add a README file"   <- IMPORTANTE: sem nenhum commit não dá pra criar release

2. Seguir os passos abaixo pra publicar a 0.1.1-alpha.

O que fazer a cada versão nova
------------------------------

1. Mudar a versão em package.json  ->  "version": "0.1.2-alpha"
   O número TEM que subir; é comparando com ele que o app instalado decide se há novidade.

2. Gerar o instalador:

       npm run dist:win

   Saem três arquivos na pasta release\ :
       Reroll-Setup-0.1.2-alpha.exe            <- o instalador
       Reroll-Setup-0.1.2-alpha.exe.blockmap   <- deixa o download da PRÓXIMA vez baixar só o que mudou
       latest.yml                              <- é onde o app lê "qual é a última versão"

3. Publicar a release. Há dois caminhos e os dois dão no mesmo lugar.

   PELO TERMINAL (mais rápido, e é o que está configurado nesta máquina):

       cd "D:\rolador ena de dado\release"
       gh release create v0.1.2-alpha Reroll-Setup-0.1.2-alpha.exe Reroll-Setup-0.1.2-alpha.exe.blockmap latest.yml --repo renatomsantana/reroll --title "Reroll 0.1.2 Alfa" --notes "o que mudou"

   O GitHub CLI já está instalado e logado como renatomsantana. Se um dia ele disser que não está
   autenticado, é rodar `gh auth login --hostname github.com --git-protocol https --web` e seguir o
   código no navegador. Numa janela de terminal recém-aberta o `gh` está no PATH; nas que já estavam
   abertas antes da instalação, não.

   Para CORRIGIR uma release que já existe (regravar os anexos por cima), é `upload --clobber` no
   lugar do `create`:

       gh release upload v0.1.2-alpha Reroll-Setup-0.1.2-alpha.exe Reroll-Setup-0.1.2-alpha.exe.blockmap latest.yml --clobber --repo renatomsantana/reroll

   PELO SITE (serve em qualquer máquina, sem instalar nada) — Releases -> Draft a new release:
       - tag: v0.1.2-alpha
       - anexar os TRÊS arquivos acima
       - publicar (não deixar como pre-release; ver a nota abaixo)

4. Pronto. Quem tiver o Reroll aberto recebe na próxima abertura.

5. Conferir que subiu inteiro (vale o minuto, porque anexo faltando só aparece como update quebrado
   semanas depois):

       gh api repos/renatomsantana/reroll/releases/tags/v0.1.2-alpha --jq ".assets[] | \"\(.name) \(.size)\""

   Têm que aparecer os três nomes, e o tamanho do .exe tem que bater com o do arquivo em release\.

Regras que não dá pra quebrar
-----------------------------

- Subir os TRÊS arquivos. Sem o latest.yml ninguém descobre que existe versão nova; sem o .exe o
  app acha a versão e falha ao baixar.

- NÃO renomear o .exe. O nome dentro do latest.yml tem que bater exatamente com o nome do anexo.
  É por isso que o instalador se chama "Reroll-Setup-..." com hífens, e não com espaços: o GitHub
  troca espaço por ponto no nome do anexo, e o app ficaria procurando um arquivo inexistente.

- Pode marcar como "pre-release" à vontade: o app liga o allowPrerelease (src\main\updater.ts) e
  enxerga as duas coisas. O que ele NÃO enxerga de jeito nenhum é RASCUNHO (draft) — release em
  rascunho é invisível pra quem está de fora, inclusive pro app.

- A versão nova precisa ser MAIOR que a instalada. Publicar 0.1.2 depois de 0.1.3 não faz ninguém
  voltar atrás.

- NÃO rebuildar um número de versão que já foi publicado. O `npm run dist:win` regrava o .exe em
  release\ com um conteúdo novo e, portanto, um sha512 novo — enquanto o latest.yml que está no
  GitHub ainda aponta pro sha512 antigo. Passam a existir dois arquivos diferentes com o mesmo
  número, e quem baixar o de lá não tem a sua mudança. Se acontecer sem querer, o conserto é subir os
  TRÊS de novo com `--clobber` (comando no passo 3); o certo mesmo é subir a versão antes de
  compilar. Foi o que se fez indo do 0.1.3 pro 0.1.4.

Onde isso está configurado
--------------------------

electron-builder.yml, bloco "publish" (owner: renatomsantana / repo: reroll). O electron-builder copia esse bloco
para dentro do pacote como app-update.yml, e é de lá que o app instalado lê o endereço. Trocar de
hospedagem depois = mexer nesse bloco e gerar de novo.

O código do lado do app está em src\main\updater.ts, e a linha de "Versão / Procurar atualizações"
que aparece nas Preferências está em src\renderer\src\components\chrome\UpdateSection.tsx.

Testar sem publicar
-------------------

Em "npm run dev" a checagem nem roda (não há pacote para substituir). Para testar de verdade é
preciso instalar uma versão MENOR, publicar uma MAIOR no GitHub e abrir o app instalado.
